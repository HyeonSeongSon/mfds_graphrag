# PREREG 잠금 전 검토 (2026-11-09)

`eval/PREREG.md` 잠금 전 검토 기록이다. **1차 검토와 의견은 Claude가 썼고, 최종 결정은 사용자가 한다.** 사용자는 각 항목의 "결정" 칸을 채운다. 비워 둔 항목은 Claude 권고대로 승인한 것으로 보지 않는다.

## 읽는 법

| 구분 | 뜻 | 사용자가 할 일 |
|---|---|---|
| **사실** | 코드 · 실행 결과 · 다른 문서와 맞는지. Claude가 실행하거나 대조해서 확인했다 | 근거만 훑어보면 된다 |
| **판단** | 무엇을 기준으로 삼을지, 어떤 한계를 받아들일지. 확인으로 답이 나오지 않는다 | Claude 의견을 읽고 결정 |
| **자기 검토** | Claude가 쓴 문안을 Claude가 다시 검토한 것. 같은 눈으로 본 것이라 놓친 것이 있을 수 있다 | 다른 항목보다 꼼꼼히 |

시간을 줄이는 방법: **사실** 항목은 표만 보고, **판단 · 자기 검토** 항목(J1~J9, S1~S2)에 시간을 쓴다. 약 20~30분을 예상한다.

**11-23 갱신:** 11-09 이후 바뀐 사정(T7 추가, 구어체 세트, 항 보조 지표, 삭제 조문 규칙)을 반영해 J3 ~ J9 · S1 · S2에 "11-23 최종 권고"를 덧붙였다. Claude 권고를 다른 세션이 여섯 차례 검토했고, 맞는 지적만 반영했다. 11-09 의견은 지우지 않고 남겼다. 행 번호(예: "83~86행")는 11-09 기준이라 지금 PREREG와 맞지 않으니 절 제목으로 찾는다. 수치는 11-23 삭제 조문 규칙을 반영한 dry-run(커밋 `6e3dcfb`) 기준이다. ### J5. 어댑터 B 채택 문턱 (214행)

- **내용:** 450문항에서 베이스 4B few-shot 대비 +10%p 이상이고 McNemar p < 0.05.
- **Claude 의견:** **그대로 둔다.**
  - 450문항이면 p < 0.05는 10%p 차이에서 쉽게 나온다. 실제로 걸리는 조건은 "+10%p 이상"이라는 크기다.
  - 450에는 held-out 80문항(18%)이 들어 있다. 어댑터는 이 의도를 학습하지 않으므로, held-out에서 베이스와 비슷하거나 더 낮을 수 있다.
  - 학습한 의도 370문항에서 약 +12%p 이상이어야 전체 +10%p가 나온다. 학습한 템플릿을 그대로 배우는 과제라 현실적인 문턱으로 본다.
- **11-23 최종 권고: 그대로 승인.**
  - 확인: held-out은 m3 + m4 80문항이다(PREREG 4-3 선택 결과). 그래서 학습한 의도는 370문항이다.
  - held-out 이득을 0으로 보면, 학습한 의도에서 450 × 10 ÷ 370 ≈ +12.2%p가 필요하다.
- **결정:** 그대로 승인 (사용자, 2026-11-23, 11-23 최종 권고대로)

### 5-4. `mask_miss` 조치 순서

1. 그 원천(T1 또는 T7) 문장을 API로 보내는 작업을 멈춘다(구어체 dev · test 생성 등). 11-25 T7 라벨 검수가 11-26 구어체 dev 생성보다 앞선다.
2. 가림 규칙(`mfds/disposition.py`)을 `amend --kind fix`로 고친다.
3. 그 유형을 다시 만든다. 구성이 바뀌면 `exclusion_ids.json`과 평가용 그래프를 다시 만들어 다시 적재한다. 가림은 읽는 시점에 적용돼 그래프 노드 텍스트에도 들어가기 때문이다.
4. AMENDMENTS에 기록한다.

- 이 경로는 PREREG 수정 절차의 늦은 처리 목록(2주차 D4 동결 전까지)에 넣는다.
- 5% · 15% 구간 규칙은 적용하지 않는다. 1건이라도 나오면 이 경로를 밟는다.
